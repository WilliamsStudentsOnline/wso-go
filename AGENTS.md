## PRs
All PRs with significant LLM contributions must be labelled `ai` on GitHub.
Explicit user consent is required to apply the `allow-breaking-changes` label.
Explicit user consent is required for PR/issue comments, resolutions, and creation.
Do not prefix PR titles with `[]` blocks, these are for human usage.
PR descriptions should consist solely of a concise bullet point list of changes (potentially including motivations & nuances), optionally prefaced by terse prose describing broader goals. May also reference issues/other PRs. Avoid test plans.
Prefer stacked PRs for more complex issues. Do not reference other PRs in the stack in PR descriptions. In particular, a full feature is _typically_ organized as:
1. Model changes (including generated SQL)
2. Queries/DAO
3. Service/library functions
4. APIs (including codegen)

## Design principles
This codebase is as much pedagogical as it is functional: contributors are often first-time coders, so in conversation, prefer explaining non-obvious decisions, asking the user to clarify ambiguous requests, and clearly presenting tradeoffs when present. Skew toward step-by-step iterative and interactive coding rather than large one-shots. Users may, however, override this as desired if they wish to rip and ship.

Ask before adding dependencies (e.g. to go.mod), editing README/AGENTS.md, or modifying scripts for local dev or CI.
Prefer following existing patterns. Search the codebase for inspiration and reference. Note, however, that this is a legacy codebase which is edited by student maintainers over many generations. As such it may contain outdated, unused, or poorly-understood code.
Keep diffs scoped to the issue at hand, and ask for consent and/or clearly note drive-by refactors and bugfixes; prefer splitting these into new branches when they are not directly tied to the in-progress feature.

Avoid disturbing existing comments unless they become outdated, and add new comments only when changes are non-obvious. Do not add comments which describe change history. Prefer single terse lines with no trailing punctuation. Avoid extremely lengthy/comprehensive documentation.

Note:
- code must align with conventions/syntax for our particular SQL/GORM libraries
- must not leak PII such as addresses or phone numbers; see sanitization code
- authentication code has some quirks; notably `RequireScopes(a, b)` is `a OR b`

## Workflows
Install full toolset for local development with `make install-tools`.
Prefer working in worktrees. Each worktree requires its own `.env` (see `.env.example`) with unique `COMPOSE_PROJECT_NAME` and ports to prevent collisions.

Consider three stages of development:
- local development (do whatever you want)
- dev server (`master`; code should be thought out, prototype-complete, and reasonable, but is subject to change/testing)
- prod server (lags behind dev and is synchronized by pinning a commit sha; code must be complete and stable)

You may **never** update prod yourself, either by running `make sync-prod` or updating `prod-sha`; such updates are human-only.
Explicit user consent required to publish a new API tag (`make publish-api`).

Run local tests with `scripts/test.sh`. Supports packages and specific test names; omitting runs full suite.
The user may run `make itest` for interactive testing.

API documentation is consumed by codegen on the wso-api-client repo, which serves as the bridge to our web and mobile clients. Swag documentation is required on every endpoint.
Generate with `make api`; never hand-edit `docs/`.
Validate with `make check-api`.
Errors are specified in `lib/errors.go` and must have unique codes.

Migration code is generated by `make migrate name=`; never hand edit `schema.sql`, `atlas.sum`, or `db/atlas/migrations/`, (legacy) `db/migrations/`.
Regenerate migrations after a rebase if local migration timestamps are behind master's.
Validate with `make check-migrations`.

Jobs code is defined in `jobs/`. Jobs are managed in `jobctl` and `registry`; explicit user consent is required for changes to these.
Ensure Makefile is aligned with registry targets.

`make fmt` to format.

`make dev` serves the API on configured ports for local development.
Authentication via LDAP is disabled for local backend development, see seeded users `student`, `admin`, `prof`, or `staff` and log in with any non-empty password.

For full-stack local development:
- in wso-go, regenerate the API and serve
- in wso-api-client, run codegen against a local `--spec` and build
- in wso-react, run codegen against the local client, point the proxy at the local backend, and serve

Query a running local DB with `docker compose exec -T mysql mariadb -uroot -psecret-mysql-password wso -e "..."` from repo root; note the ephemeral test DB is distinct.
Reset local development DB with `make dev-reset`; this requires explicit user consent.
Generate a new seed DB for future local developers with `make dev-seed-dump`; this requires explicit user consent. Prefer this over defining fixtures/seeders.
